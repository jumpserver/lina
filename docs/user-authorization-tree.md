# 用户授权树实现与性能优化说明

整理日期：2026-09-09。本文汇总本次授权树重构的实现说明及此前远端测试结果；性能数据不是通用承诺，缓存命中率为估算，尚无生产命中率监控数据。

## 1. 核心设计

**用户授权树不单独存储。系统根据用户有效授权规则裁剪公共资产树，按需返回节点；节点数量独立批量计算，并使用 15 秒短缓存。**

主要策略：

- 不创建、刷新用户专属授权树中间表。
- 将用户和用户组授权查询拆开，避免多对多 JOIN 产生巨量中间结果。
- 压缩冗余授权节点，利用节点路径查找后代和补齐祖先。
- 树节点、节点数量、右侧列表分别请求，互不等待。
- 节点和资产分页加载，每批 100 条；先加载直接子节点，再加载直接资产。
- 数量按一批节点计算，避免逐节点重复执行大查询。
- 每个 API 内复用一个 `UserPermAssetUtil`；不同请求通过 Redis 共享短缓存。

## 2. 数据关系与树结构

```text
用户 / 用户组
    └── AssetPermission 有效授权规则
          ├── 直接授权节点 Node
          └── 直接授权资产 Asset

Node ← 多对多关系 → Asset
```

真实节点使用物化路径表示父子关系：

```text
组织根节点：5
子节点：    5:9
孙节点：    5:9:3
```

节点本身及其后代的判断：

```python
key == granted_key or key.startswith(f'{granted_key}:')
```

`PermNode` 是 `Node` 的代理模型（`Meta.proxy = True`），没有独立数据库表。它保留授权节点语义、虚拟节点构造等能力，不是需要刷新维护的授权树中间表。

## 3. 前后端请求流程

```text
打开页面
├── GET 授权树根节点 / 子节点
│     └── 节点显示后，POST tree-metrics 获取当前批次数量
└── GET 右侧授权资产列表

展开节点
├── 分页加载直接子节点，每批 100 条
├── 对已返回节点异步获取数量
└── 子节点加载完后，分页加载直接资产，每批 100 条（Luna）
```

主要接口：

```text
GET  /api/v1/perms/users/{user_id}/nodes/children-with-assets/tree/
POST /api/v1/perms/users/{user_id}/tree-metrics/
GET  /api/v1/perms/users/{user_id}/assets/
```

Lina 用户详情、工作台以及 Luna 复用 Core 的授权范围计算能力。Lina 对应页面的授权树只展示节点；Luna 还加载资产。

`tree-metrics` 按实际已加载资源批量请求，不再固定使用 200 条上限。

## 4. 授权树节点如何计算

### 4.1 获取有效授权规则 ID

先读取用户与当前组织维度的 15 秒缓存。未命中时：

1. 获取用户加入的组织。
2. 从规则—用户关系表查询直接关联用户的规则 ID。
3. 查询用户所属用户组。
4. 从规则—用户组关系表查询组关联规则 ID。
5. 在 Python 中合并去重。
6. 过滤有效期、启用状态及用户所属组织等规则条件。
7. 将最终 ID 元组写入缓存。

简化逻辑如下，非完整源码：

```python
permission_ids = cache.get(cache_key)
if permission_ids is None:
    direct_ids = query_user_permission_ids(user)
    group_ids = query_user_group_ids(user)
    group_permission_ids = query_group_permission_ids(group_ids)
    candidate_ids = set(direct_ids) | set(group_permission_ids)
    permission_ids = query_valid_permission_ids(candidate_ids, joined_org_ids)
    cache.set(cache_key, tuple(permission_ids), timeout=15)
```

原实现将用户、用户组及规则关系一起 JOIN，再使用 `OR + DISTINCT`。一条规则同时关联大量用户和用户组时，中间结果会成倍放大。拆分查询后只读取必要的关系行，再合并 ID。

实现还使用 `Cast(..., CharField())` 减少大量 UUID 对象构建和集合哈希的开销。

### 4.2 压缩直接授权节点

规则对应的授权节点可能重复覆盖：

```text
原始：5:2、5:2:1、5:2:1:8、5:4、5:4:7
压缩：5:2、5:4
```

`Node.clean_children_keys()` 删除已被授权祖先覆盖的后代节点。后续查询只处理压缩后的授权锚点。

如果某个组织根节点已直接授权，该组织只需保留根节点，其他授权节点均被覆盖。具体组织下可以直接走完整组织授权路径；全局组织下逐个组织判断。

### 4.3 处理直接授权资产

- `PERM_SINGLE_ASSET_TO_UNGROUP_NODE=True`：直接授权资产放在虚拟“未分组”节点，不依靠它们恢复普通节点路径。
- 配置关闭：查询直接授权资产所在节点，排除已经被节点授权覆盖的位置，再补齐这些位置的祖先。

### 4.4 补齐可见祖先

可见锚点来自：直接授权节点，以及配置需要时的直接授权资产所在节点。

```text
授权锚点：5:9:3:7
可见路径：5 → 5:9 → 5:9:3 → 5:9:3:7
```

这只构造节点键集合，不向数据库写入用户专属节点。

### 4.5 返回直接子节点

```python
# 简化逻辑
if is_node_fully_granted(key):
    children = Node.objects.filter(parent_key=key)
else:
    children = Node.objects.filter(
        parent_key=key,
        key__in=visible_ancestor_keys,
    )
```

完全授权节点返回全部直接子节点；仅作为可见祖先的节点，只返回能够通向授权资源的分支。

## 5. 节点下资产列表如何计算

| 查询场景 | 完全授权节点 | 部分授权节点 |
|---|---|---|
| 节点直接资产 | 返回直接关联该节点的资产 | 返回直接关联该节点且直接授权的资产，结合未分组配置处理 |
| 节点及后代资产 | 返回整个子树资产 | 合并子树内节点授权资产与直接授权资产 |

最终按资产去重。同一个资产属于多个节点，列表中仍只出现一次。

## 6. 节点数量的定义

**数量表示当前节点及其所有后代中，用户被授权的唯一资产数量。**

```text
A
├── B：资产 X、Y → 数量 2
└── C：资产 X、Z → 数量 2

A 数量为 3，而不是 4。
```

因此不能简单相加子节点数量。资产跨节点关联会导致子节点数量之和大于父节点数量。

## 7. 节点数量如何批量计算

### 7.1 先批量读取缓存

每个节点的缓存维度是用户、节点所属组织、节点 ID：

```text
perms:user-granted-tree:{user_id}:{node_org_id}:asset-count:{node_id}
```

通过 `cache.get_many()` 一次获取整批结果，只计算未命中的节点，再用 `cache.set_many(..., timeout=15)` 批量写入。

### 7.2 完全授权的组织根节点

如果组织根节点确实已完全授权，直接统计组织资产：

```python
Asset.objects.filter(org_id=node.org_id).count()
```

如果根节点只是因为局部授权而可见，不能使用这个捷径。

### 7.3 完全授权的普通节点

一次查询整批目标子树涉及的资产—节点关系，并按资产排序：

```python
relations = (
    relations.annotate(asset_key=Cast('asset_id', CharField()))
    .order_by('asset_key', 'node__key')
    .values_list('asset_key', 'node__key')
)

for asset_id, node_key in relations.iterator(chunk_size=10000):
    # 将当前资产计入匹配的目标节点；同一目标对同一资产只计一次。
    ...
```

特点：

- 一次扫描计算一批节点，而不是每个节点单独扫描。
- 同一资产在同一目标子树出现多次，只统计一次。
- 流式处理，不为每个目标保留完整资产集合；数据库仍需完成排序。
- 本次扫描缓存节点路径与目标节点的匹配结果，减少重复前缀判断。

### 7.4 部分授权节点

例如统计 `5:9`，用户授权了 `5:9:3`、`5:9:8:2` 和一个位于 `5:9:6` 的直接资产：

1. 计算目标子树与已授权节点子树的交集，选择需要扫描的更具体路径。
2. 将这些授权子树里的资产加入目标节点的集合。
3. 未分组配置关闭时，将目标子树里的直接授权资产加入同一集合。
4. 集合长度就是唯一授权资产数量。

```python
# 简化逻辑
target_assets[target_key].update(node_granted_asset_ids)
target_assets[target_key].update(direct_granted_asset_ids)
counts[target_key] = len(target_assets[target_key])
```

此路径必须处理两种授权来源的重叠，内存开销随唯一“目标节点—资产”匹配数量增加，比完全授权路径更高。

## 8. 缓存范围与命中率

| 内容 | 维度 | 生命周期 |
|---|---|---|
| 有效授权规则 ID | 用户 + 当前组织 | 15 秒 |
| 压缩后的直接授权节点键 | 用户 + 当前组织 | 15 秒 |
| 直接授权资产所在节点键 | 用户 + 当前组织 | 15 秒 |
| 节点授权资产数量 | 用户 + 节点所属组织 + 节点 | 15 秒 |
| 类型树（独立路径） | 用户 + 当前组织 + 语言 | 60 秒 |
| util 内的惰性属性 | 当前 Python 对象 | 单次请求 |

读取不会延长 TTL。各键独立生成、独立过期，因此一次请求可能混合命中和未命中。授权变化存在短暂缓存一致性窗口；不能把多个独立缓存层简单理解成严格统一的 15 秒快照。

**目前没有实际命中率监控，不能宣称生产命中率达到某个百分比。**

页面短时间连续请求通常共享用户和组织键。假设 6 个顺序请求均在 15 秒内，只有第一个 miss，那么该公共缓存键的命中率约为 83%。这不代表节点数量缓存也有同样命中率：每个新节点首次计算仍然 miss。

当前没有分布式锁。多个并发冷请求可能同时 miss 并重复计算。

同一键在理想化稳定随机请求下，固定 TTL 的粗略命中率为：

```text
命中率 ≈ λT / (1 + λT)
λ：每秒请求次数；T：15 秒
```

| 同一键请求频率 | 理论估算 |
|---|---:|
| 每秒一次 | 94% |
| 每 5 秒一次 | 75% |
| 每 10 秒一次 | 60% |
| 每 30 秒一次 | 33% |

真实结果取决于用户、组织、节点的访问集中程度与并发时序。

## 9. 索引优化与数据库兼容

新增符合实际查询方向的复合索引：

```text
规则—用户关系：(user_id, assetpermission_id)
规则—用户组关系：(usergroup_id, assetpermission_id)
资产—节点关系：(node_id, asset_id)
```

原有唯一索引通常为反向顺序，不能同等有效地支持从用户、用户组或节点查关联资源。新索引帮助数据库读取需要的 ID，减少扫描与回表。

迁移使用 Django `schema_editor.add_index()`，实现面向 PostgreSQL、MySQL 和 MariaDB。此前验证包含本地 PostgreSQL 迁移及远端 MariaDB；未提供 MySQL 独立实测数据。

## 11. 最坏情况和剩余瓶颈

| 授权或访问形态 | 为什么慢 |
|---|---|
| 用户关联大量规则或用户组 | 冷请求仍需读取、合并和过滤大量关系 ID |
| 大量互不覆盖的深层叶子节点授权 | 节点键无法有效压缩，需要处理大量路径和祖先 |
| 大量直接资产授权，且未分组关闭 | 必须从资产反查节点位置并补齐祖先 |
| 同一资产挂载很多节点 | 关系行数远大于资产数，扫描和去重成本增加 |
| 一批大子树只有零散部分授权 | 需合并节点授权与直接授权，并维护去重集合 |
| 全局组织下跨很多组织零散授权 | 权限、路径和扫描范围扩大 |
| 大量并发冷请求 | 无缓存锁，可能重复计算造成瞬时压力 |

数量计算的主要规模因素是**相关资产—节点关系行数及重叠程度**；权限范围计算则主要受**用户相关授权规则和用户组关系数量**影响。

完全授权组织根节点能够使用快捷路径。大量分散叶子节点与直接资产混合授权是更差的形态，但不能为了性能扩大用户权限；授权范围必须以实际业务需要为准。

后续可根据真实负载增加缓存命中率、查询耗时、扫描行数监控，评估请求合并或缓存失效策略。

## 13. 对外讲解的简短版本

> 用户授权树通过实时裁剪公共资产树生成。系统先分别查询用户和用户组关联的有效规则，再把授权节点压缩为最小锚点集合，利用节点路径补齐祖先，按需分页返回可见分支。数量独立批量计算：完全授权节点流式扫描资产节点关系，部分授权节点合并两种授权来源并准确去重。覆盖索引和 15 秒短缓存减少重复查询。在此前测试环境中，七万授权资产场景的批量节点数量冷计算约一秒，缓存后约几十毫秒；实际性能仍取决于授权分散程度、关系行数和并发量。
